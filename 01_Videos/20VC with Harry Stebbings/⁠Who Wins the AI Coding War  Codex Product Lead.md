## Summary

This note examines the AI coding market as a race shaped by workflow integration, developer trust, and product design rather than pure model benchmarks. A Codex product perspective matters here because coding tools win only when they fit how real developers already work.

## Key Insights

- AI coding products compete on ergonomics and adoption loops, not just raw capability.
- The market is likely to support multiple winners unless one workflow becomes overwhelmingly dominant.
- Product leadership in this space requires balancing autonomy, trust, and clear human override.
- The useful question is not who demos best, but who becomes part of the default stack.

## Key Quotes

- "Who wins the AI coding war?"
- "The default workflow is where the power accumulates."
- "Trust matters as much as capability."

>> 简单回答：极其重要。  
>> 那这会不会变成一种推理垄断？现在你有，竞争对手没有？  
>> 这只是我的个人观点，但我不认为最后会进入一种垄断状态。我觉得竞争压力太大了，最后会有多个答案。不过我们很快会公布和那次合作相关的更多消息，我非常兴奋。即便如此，像 GPT-5.3 Codex 这样的模型，本身就比前代高效得多。我们听到的反馈是，人们现在已经觉得它速度很有竞争力了。你既可以从模型本身入手，也可以从推理实现层面入手。我们最近刚做了一次改动，API 里模型的响应快了大约 40%，Codex 里快了约 25%。所以速度非常重要，而我们是在硬件、推理实现、模型三个层面同时推进。

>> 你刚刚提到把东西交到用户手里。说到推理，我有个好朋友是 Jason Lemkin，他说“推理就是新的销售和营销”。意思是，你不再花那么多钱养销售和市场团队，而是把钱花在 inference 上，让用户更快看到价值、更快上手。这像是 PLG 的下一代。  
>> 嗯，我对这个说法有点挣扎。我觉得在一个“任何人都可以构建、构建越来越容易”的世界里，真正难的东西是什么？我认为，和客户建立关系、真正知道客户需要什么，比以往任何时候都更难，也许甚至更难了，因为市场上的软件只会越来越多。另一些真正难的事，是做对产品、把产品做得高质量。所以回到销售和营销，我不觉得它会消失。我反而觉得，随着市场愈发拥挤，这件事只会更难。

>> 我能问一下，你们现在内部有多少代码是由 Codex 产出的？我记得 Claude for Work 的 Boris 说过，接近 100%。  
>> 我先说我自己，再说团队。就我认识的大多数人来说，他们现在基本都不再打开编辑器了。  
这其实是一个渐变的过程，但如果你从外部看，真正的拐点大概是 GPT-5.2 Codex。那个模型突然变得能更长时间运行、能端到端处理任务、能管理上下文、能更好地遵循指令。于是我们看到了一个非常明显的转折点，这也是我们后来决定做 app 的原因之一。  
在 GPT-5.2 Codex 之前，大家使用 AI 写代码，大多还是 tab completion，或者和模型 pair programming。换句话说，你还是得坐在键盘前面，手放在键盘上，AI 也许帮你处理一点小任务，但你仍然在主导。  
而到了去年 12 月，我们突然切换到了另一种方式：我直接把任务完整地委托给它。我会先让它做个计划，确认规格没问题，然后就让它自己去做。这完全是另一种工作方式，而且这种变化此时此刻还在继续发生。  
所以我们上周发布 Codex app，很大一部分原因，就是想做一个更符合“委托”而不是“结对”的交互形态。它支持同时委托给多个 agent。即使在 OpenAI 内部，这种工作方式的变化也非常巨大。  
我没有精确比例可以告诉你，但我会说，绝大多数代码已经是 AI 在写了。而且现在大多数人甚至都不再打开 IDE。即便打开，也更多是在界定接口、一起讨论计划，然后让 AI 来补全实现。代码本身，已经不再由人类亲自逐行去写。

>> 24 个月后，IDE 还会是技术栈的一部分吗？  
>> 如果从“integrated development environment”的字面定义说，这个词太松了，几乎什么都能叫 IDE，所以这个定义没什么帮助。按这个标准，甚至 Codex app 也可以算 IDE，但我不这么看。我理解中的 IDE，是一个功能很强的编辑器。我们刻意没有在 Codex app 里做文本编辑，就是想让它的使用方式更清晰。它在管理多个 agent、委托任务、审查变更这类事情上有很多能力。它还有非常醒目的 skills，这是开放标准，对于做非编码工作也很有帮助，比如分诊任务、监控部署之类。但它没有文本编辑。

>> 如果内部大量代码都是 Codex 写的，那你们怎么做 code review？AI 会负责内部代码审查吗？  
>> 这里有几个层次。首先，你想做什么、也就是 spec 或 plan，会变得比以往任何时候都更重要。你需要先从架构层面想清楚：这段代码到底应该怎么工作。  
我们最近推出了一个很醒目的 plan mode，和别家不太一样。你先让 agent 离线去提出一个长计划，然后它会回来问你：你是否同意这个方案、是否有输入。这很像一个刚加入团队、还不熟悉代码库的新同事，在动手之前先给整个团队提交一份 RFC。  
所以，即便这还不是正式意义上的 code review，我也会说，“计划评审”会变得越来越重要，因为我们正在进入一个更多“委托式协作”的阶段。  
然后才是真正的 code review。我经常听到很多人，尤其是开源圈的人，抱怨“AI slop”——一堆垃圾 PR。有人给开源仓库提交 PR，但那些 PR 很差，提交的人甚至可能连测试都没跑，更别说审代码了。这个问题是真实存在的。  
所以一个非常常见的做法，是让 Codex 先 review 它自己写出来的 PR 或变更。Codex 在这件事上其实非常强。我们明确训练过模型去做好 code review，包括让它能给出高信号、低误报的反馈。也就是说，当它提出问题时，你真的可以比较信任。  
因此，我们不仅鼓励团队内外的人主动让 Codex 做 review，你甚至可以把它设置成自动 review。几乎 OpenAI 内部所有代码，一旦推送到合适的仓库，都会被 Codex 自动审一遍。  
一个很好玩的现象是，有些人第一次意识到我们模型有多强，不是因为直接拿 Codex 写代码，而是让 Codex 去 review 其他模型写的代码，然后他们会说：“糟了，我可能干脆应该直接用 Codex 来写代码。”

>> 你刚刚提到，有些人可能很久没试过，或者最近又回来了。这个品类的“留存”你怎么看？我记得很久以前 Tom Blomfield 发过一条推文，大意是不同 provider 之间迁移实在太容易了，不管是 Cursor、Claude Code 还是 Codex。用户到底有多粘？你怎么看 retention？  
>> 我们在 Codex 上采取了一个有点反直觉的策略，就是把它做得非常开放。Codex 的核心 harness 是开源的，我们一直在尽可能让切换变得更容易。比如说，去年我们第一次发布 Codex 时，就建立了一个惯例，叫 `agents.md`。本质上这只是一个给 agent 放说明的文件。我们没把它命名成 `codex.md`，因为我们希望所有 agent 都能用。现在基本除了某个惯犯之外，大家都在用 `agents.md`。  
就在上周，我们还推动了另一个标准：skills 这种给 agent 提供说明和脚本的能力，应该放在一个中性命名的 `agents` 文件夹里，而不是 `codex` 之类的目录。大家也都跟进了，除了那个老熟人。  
所以我们其实是希望开发者拥有很多选择，并且我们还在努力让尝试不同工具变得更容易。

但话说回来，当前这类 coding task 之所以容易切换，是因为它们很“封闭”、很“中性”。你可以把它想成电视剧里的“单元剧”：上游你有一个任何 agent 都能读的 `agents` 文件，也有任何 agent 都能用的 skills；然后你让 agent 写代码，它输出一个 patch，这个 patch 最终进入 git。也就是说，两端都是相对 vendor-neutral 的，现在切换自然很容易。  
可一旦 agent 开始做的不只是写代码，而是更一般的工作——不管是给软件工程师，还是给任何 builder——它就会开始和更多系统交互。也许它会和 Sentry 对接，也许它会和 Google Docs 对接。到了那个时候，agent 就会变得更粘，因为你决定把某个 agent 接入某个系统，本身就是一个非常 sticky 的决策。  
尤其在企业里，如果你真的信任一个 agent 能访问这些工具，那你一定同时会非常看重它是否有良好的安全护栏、sandbox、控制能力。而这种事你不会想重复做很多遍。  
所以我们从一开始构建 Codex 时，就知道这一天会到来。我们做了最保守的 sandboxing 方案——sandboxing 就是一组操作系统层级的控制，决定 agent 能做什么、不能做什么。

>> 我特别喜欢《Seven Powers》这本书，它讲企业如何积累可持续优势，其中之一就是粘性、留存。如果你和我在同一个 Codex 团队里，我们该怎样设计出真正有留存力的行为模式和产品机制？怎么让用户留在 Codex，而不是在 Cursor 或 Claude Code 出了更好的模型时就切走？  
>> 这个问题很有趣。一方面，我们当然会想这些，因为我们也在经营一项业务；但另一方面，我们的使命是要“安全地把 AGI 的好处带给全人类”。所以对很多听众来说很反直觉的一点是：Codex 团队的任务并不只是守住 Codex。  
>> Alex，我知道，但你的工作就是让 Codex 赢。  
>> 我们的工作是分发智能。没错，我们当然也想把 Codex 做大做强，但 OpenAI 是个很不寻常的地方：我们花很大力气训练模型，然后把模型提供给竞争对手。  
>> 这对我这个风投来说真的太难理解了。你知道的。  
>> 我完全知道。这就是 OpenAI 很特别的地方。因为我们玩的时间尺度很长，所以竞争对手变强，对我们来说反而也是一种学习。实际上是有帮助的。  
我们当然也在努力让 Codex 增长，而且拥有很大的优势：ChatGPT 带来的分发优势、我们自训模型带来的能力优势、我们可以在别人之前拿到新模型、为它们构建更合适的 harness。我们是在认真地打赢这场仗。  
但与此同时，我们也在打一个更长的局：我们把模型提供给所有人，推动开放标准，让所有人都能用。

>> 那如果我硬要用风投语言来问：最后决定谁赢的那个因素到底是什么？是 GTM，还是产品，还是算力？  
>> 如果从 OpenAI 的层面说——这当然高于我的职级——我会说是算力优势，以及拥有最好的模型。为了做到这一点，我们需要把业务做好、产生收入。  
但有一点也很有意思：像 Codex 这种把研究和产品放在同一支团队里的做法，会形成一种良性循环。你把产品做成功，实际上也会反过来给模型研发施加更强的压力，让模型进步得更快。  
如果只说产品层面，我觉得最重要的事，是把产品做到“人们真的想用”。而且像我前面说的，我们想做的是给个体使用的产品，让人们通过频繁使用变得熟练，然后再把自动化一层层拉进来。  
这听起来也许有些反直觉，但我相信，这种路径最后会比纯粹从企业工作流自动化出发更有影响力。  
当然，到了企业端，GTM 就非常重要了。如果我们只是走进一家企业，说“嘿，我们来了，你们可以随便用”，那是行不通的。你需要大量教育工作，还要支持配置，帮他们把这种工作方式传播到更大的团队里。你要见 developer experience 的负责人，理解他们希望团队怎么工作，然后给他们工具，让这套方式能扩散出去。

>> 那你和 Sam 或 Brad 坐下来时，真正的北极星指标是什么？  
>> 第一指标其实不是收入，而是活跃用户。  
>> 怎么定义？周活？  
>> 对，我们看周活。就是某个人有没有真的在产品里做一次 turn、发一次 prompt。  
>> 但如果它真的在替代 IDE，日活不是更合理吗？  
>> 我觉得很快日活会更合理。只是我们最开始用周活比较方便。但我同意你的批评。我们应该去到一个世界：面对任何任务，你的第一反应都是“让我先问下 agent 能不能帮忙”。就像以前面对任何信息需求，你第一反应是去 Google；后来是去 ChatGPT；接下来这一阶段应该是：面对任何任务，不只是找信息，你都先去一个统一入口，让它帮你完成至少一部分。

>> 说到“聊天作为统一入口”，我很好奇。它当然对忙碌的人非常高效，但也有人说，聊天界面只是适合高效人群，大多数人其实想要浏览器式发现、图形界面式互动。你觉得“聊天”会是未来 AI 面向人类的持久 UI 吗？  
>> 简单回答是：会。但我觉得要拆成两部分来看。  
如果我们想象一下未来，像科幻电影那样，AI 应该是什么样？我一直觉得科幻对未来的预测很准，而且通常很简单，因为故事必须清晰。我觉得未来会有一个“你可以用任何方式和它交谈、讨论任何事情”的存在。  
我不认为你会想：“现在我要去一个专门的 coding AI 界面”“现在我要去一个专门的 sales AI 界面”。那太烦了。  
所以我认为会有一个以聊天或语音为核心的通用界面，它是万物的入口，你可以把它加进任何群聊，也可以就任何事情和它说话。  
但与此同时，如果你是某个领域的 power user，你也不会希望自己完全被聊天界面中介掉。就像你有一个执行助理，但你不能永远只能通过助理工作，那也很烦。你还是希望最后能直接去看 show notes、亲手改内容。  
所以我认为未来会是：一边是 chat/voice 这种通用入口；另一边是围绕具体工作流设计出来的专门 GUI。比如我会通过聊天来准备播客，但真正看产品、看代码时，我还是会进 Codex app。营销人可能不会下载 Codex app 去问产品问题，但他可能会进入一个非常定制化的广告分析界面。

>> 这个回答默认了最终还是面向消费者的人机交互。但我其实还想问 agent-to-agent。比如费用报销：我的 agent 帮我提交去旧金山出差的报销单，企业另一端有个 agent 在合规系统里审批。你怎么看 agent-to-agent 这件事？  
>> 我最快速的回答是：我们在构建 Codex 的过程中发现，最适合 Codex 使用的接口，往往也是最适合人类使用的接口。  
比如最简单的例子：跑测试。很多测试框架默认会把所有测试输出全都打出来。对人来说，这很糟糕，因为你得在海量日志里找出失败测试；对 AI 来说也一样糟糕。但如果你只输出失败测试，那对人更好，对 agent 也更好。  
所以我猜，未来 agent-to-agent 的交互点，大体也会和“如果中间还有个人”的设计相似。这是好事，因为它意味着你可以逐步替换系统，而不是一下子全部重构。

>> 我在节目里提到过这个市场，有另一家大公司的一位投资人说，你一定要问他一个问题：Anthropic 现在是不是已经拥有了 coding 数据护城河？他们是不是已经把数据全拿走了？  
>> 我 definitely 不觉得他们在 coding 数据上有明显优势。从我们目前看到的情况——当然研究团队会更有发言权——我们感觉自己已经有足够的数据来训练非常好的 coding 模型。  
我反而觉得，现在更有意思的数据，不是 coding，而是“知识工作”数据。因为这类数据通常并不存在于互联网公开语料里。于是你就会开始思考很有趣的问题：怎么让模型在这类事情上变强？也许你得付钱让人去模拟任务流程，采集 trajectory；也许你会去收购一些已经不再独立经营但内部数据很丰富的公司，比如有 Slack 数据的公司。相比 coding，知识工作任务的数据分布其实难得多。

>> 那你怎么看和这些数据提供方的关系？比如 Mercor、Scale、Invisible、DataDome 之类的。你们会在这些数据服务商上多花十倍的钱，还是说“太贵了，我们自己搞数据采集”？  
>> 我们的核心想法一直是：怎么移动得最快。自己内部从头搭这些能力，时间成本很高，而我们的团队很小。所以目前如果要大规模跑数据计划，通常我们还是会借助这些公司。

>> 回到消费者这一面。你会不会和 Lovable、Replit 之类的低门槛建站/建应用工具在两年后形成竞争？Codex 会不会面向“普通人做个 about me 页面”这种场景？  
>> 现在看起来，我们还没有非常直接地正面竞争。但你可能看过我们的超级碗广告，核心意思就是：“你可以直接开始构建东西。”  
有了 app 之后，我们发现很多技术背景没那么强的人也开始造东西，他们做的往往是更偏 hello-world 的项目。所以我觉得我们肯定会在一些使用场景上和那类工具产生重叠。  
尤其上周有个很重要的变化：我们开始在免费版和 Plus 版 ChatGPT 里都提供一定量的 Codex 能力。这意味着大量人会在免费 ChatGPT 里第一次打开 Codex，用它去造很简单的东西。以前他们可能会去一个专门工具，现在可能直接就在 ChatGPT 里做了。

>> 有没有什么事，是你特别想做，但现在还做不了的？  
>> 最近几周我们过得其实挺不错，所以我挺兴奋的。  
>> 你刚说“最近几周不错”，我能感受到。团队会明显感受到势头的变化吗？无论是正向还是负向？  
>> 会，非常会。  
如果看 Codex 的历史，去年我们最早推出的是一个非常酷的概念：给 agent 一台云端电脑，让你可以同时让很多 agent 为你工作。这个想法很棒，但老实说，当时它没后来做的东西那么有效。  
从去年 8 月、尤其是 GPT-5 之后，我们开始强推交互式 coding，而这正是市场竞争最激烈的地方。然后我们就一路狂飙。公开可说的指标是，自那之后我们增长了大概 20 倍；光从 12 月到现在又翻了一倍左右。  
而上周带来的变化更强：我们已经有了最聪明的模型，GPT-5.3 Codex 进一步巩固了这一点；之前我们收到的负面反馈是“模型比较慢”“不够有趣”“工作时和人沟通得不够好”。我们已经针对这些问题做了改进。  
再加上我们推出了 app，市场对 app 的反馈非常强烈。以前我们的主力使用面是 IDE extension，CLI 也没那么 polished；但 app 一出来，大家普遍觉得这是一个高质量、而且直觉上很简单的体验。甚至之前最大的批评者都被转化了。然后我们又有超级碗广告，又把它放到了免费层。  
所以回到你刚才的问题：如果说我最想马上去做什么，那第一就是重新回到 cloud。去年我们从“主打云端 agent”转向“主打交互式使用”，原因很简单：如果在最终用户还没形成熟练心智之前，你就过早跳到工作流自动化，那这东西只会成为少数 power user 的幻想。  
但一旦你有了一个大家每天都在用、每次用都在变得更好的基础产品，那么再往上一步，把任务放到云端独立跑，就不再是一个那么大的跳跃。所以我觉得现在是时候重新把云端产品做深，并且和本地产品做更紧密的一体化。  
第二件想做的事，是去解决那些“被低估的瓶颈”。代码生成已经快要变成一件很平凡的事了。真正难的是你前面说的那些：我们怎么知道代码质量够好？怎么知道方向是对的？这些瓶颈还没有被足够重视，也没有被投入足够多资源。  
我想去到一个世界：agent 真正“去瓶颈化”了，你会放心让它完全拥有一个微服务、内部工具，甚至能在接收用户反馈后自动迭代，而不用每次都经过人工审核。这不仅是智能问题，也是安全和控制问题。

>> 你觉得 benchmark 和 eval 到底该有多大权重？  
>> 这个答案可能有点烦人：我觉得要看一些，但不能只看这个。它们对“智能”这个维度很有价值，特别是在 benchmark 还没饱和的时候，明显进步是非常有意义的。  
但你还是得把它和“用起来的感觉”结合起来评估。而这件事非常 vibes based。无论内部还是外部，我都越来越惊讶于，人们对模型体验的评价，其实有多么“看感觉”。  
>> 生活本来就很看 vibes。人愿意和自己喜欢的人一起工作。  
>> 对，关系很重要。

>> 我下一个问题有点狠：我觉得 Cursor 今年会损失一半收入，会从 10 亿掉到 5 亿。你同意吗？  
>> 我能不能不评论？  
>> 可以，当然。  
>> 更认真一点说，我觉得很难判断。他们确实做出了一个很成功的业务，我们在企业场景里也经常碰到他们。  
我认为 Cursor 最厉害的一点，是它真正做到了“在用户所在的位置迎接用户”。很多开发者一直在用 IDE，也一直在用 tab completion，哪怕是在 AI 之前就这样。所以 Cursor 的策略非常顺滑：你本来就在用 VS Code，那你切到 Cursor，工作流几乎不被破坏，只是某些部分变得更好了。  
VS Code 当然也依然很强，我自己还在用。但 Cursor 这种“你原有的一切几乎不变，只是更强了”的叙事，对很多人很有吸引力。  
所以我对 Cursor 的理解是：他们想先在用户原本的工作流中扎根，再逐渐往更深的 agentic 功能上加。这种客户关系本身就是有价值的，不会轻易消失。

>> 你觉得他们开始自己做模型，是个正确的战略决定吗？  
>> 很难说，但我能理解。市场里确实存在那样一种空白：你需要一种足够快、足够配合那种工作方式的模型。  
我的猜测是，他们可能判断：当时无论是我们还是别家提供的模型，在速度上都没完全满足他们用户的期待。比如我第一次用 Cursor 的神奇时刻，就是第一次按下 command-K，选中一段代码，直接做 in-line editing。我当时觉得“这太牛了”。  
如果他们发现大量用户就是想保有这种“和 AI 一起结对工作”的模式，而之后才会逐步走向更高级的委托式工作流，那么为这种路径训练一类快模型，是有道理的。

>> 从投资角度看，这个市场的最终结构会是什么样？是像 Uber/Lyft 那样，还是像 AWS/Azure/GCP 那样三分天下？  
>> 我觉得长期看，可能会是更少的玩家捕获大量价值。原因是，我们现在处于一个过渡阶段：agent 主要还是擅长 coding。去年有些人以为 agent 很快也会在其他很多领域变得同样好，但那并没有发生。所以行业里真正达到 PMF 的，基本还是 coding agent，只是零星有些客服之类的窄场景。  
但我觉得这只是暂时的。长期看，我们会得到能够替你做各种事情的 super assistant。你可以对它说任何事；如果你恰好在某个具体领域深挖，它也会有相应的专用 UI。  
在那个世界里，你不会想在公司里有 12 个不同的 agent，每个员工还得自己琢磨该找哪个说话。那样他们根本形成不了 fluency，也就无法把自动化真正拉进自己的角色里。  
如果你有一个统一的东西，什么都可以和它说，那你的 onboarding 就变成“去跟它聊任何你需要的事”。然后人们会形成肌肉记忆，它会变成工作的重力中心，团队会围绕它分享最佳实践、办 hackathon，最终你只会剩下少数几个这样的系统。

>> 你前面说 agent 现在主要只是在 coding 场景里真正普及。假设我是一个投资人，我今天要投那些能长期积累价值、服务客户的公司。很多人现在认为，大型 SaaS 公司的收入耐久性已经接近零，SaaS 已死，因为 Anthropic 之类模型公司会来吃掉它们。你会给我什么建议？  
>> 我的出发点是：所有东西最终都是给人用的。不然还有什么意义呢？就算是 SaaS 也是为人设计的。  
所以我首先会问：这家 SaaS 公司在另一端是否拥有一个“人”的关系？如果有，我怀疑它不会轻易消失。或者，它是否拥有一个非常重要的 system of record？那也大概率不会消失。甚至我觉得，在今天，这两点的重要性比以前更高。  
相反，如果它只是一个胶水层，既不拥有最终用户关系，也不拥有关键 system of record，那我就会更紧张。虽然我不是这方面的专家，但那类公司让我更不安。

>> 那按这个逻辑，Salesforce 和 ServiceNow 现在跌那么多，就不应该。  
>> 我也觉得不应该。你觉得呢？  
>> 我也觉得市场反应夸张了。当然有些公司确实应该跌。比如恕我直言，我觉得 Dropbox 的处境很难。但像 Monday.com 这种，面向大量 SMB 和消费者用户，他们的需求并不复杂：加任务、完成任务、看历史任务、分配给新成员。你当然可以 vibe code 一个待办工具，但值不值得、是不是划算，其实未必。所以我觉得这波反应非常夸张。  
>> 我同意。而且现在造产品容易了，反而更要求你是那种真正想清楚分发、客户、领域理解的创始人。过去有一段特殊时期，你可以单纯投一个“会做产品的人”，暂时不那么在乎他对客户、分发、go-to-market 有没有清晰判断，因为当时“做出好产品”本身极难。但那是个异常时期。现在也许不是该投那种创始人的时候了，因为做出好产品本身相对容易了。你要回到投“真正理解客户、理解分发”的创始人。

>> 那如果你在我的投资团队里，你会怎么看哪些方向值得投、哪些方向不会被模型公司轻易吞掉？  
>> 我有点想直接说我不知道。现在对投资人来说真的很难，市场变化太快了。  
不过如果硬要答，我的答案有两部分：  
第一，我会看那些有“实体基础设施”的东西。比如能源供应，我不觉得 OpenAI 会自己去做。  
第二，是金融科技、银行集成、非常复杂的金融产品。OpenAI 不太可能去东南亚和 500 家银行逐一建立关系。  
>> 我也同意。归根结底，如果你进入的是那种特别复杂、客户关系和市场认知极其重要的行业，那依旧很有价值。

>> 人才战争有多严重？在英国，我们看旧金山，会觉得“最好在欧洲建公司，因为在旧金山招人太难、留人也太难”。我错了吗？  
>> 现在人才争夺非常激烈。OpenAI 的品牌确实很强，这让我们能够吸引很多人，但即便如此，我们依然要花非常多精力去 close 我们真正想要的人。不是说你在 OpenAI 就可以随便挑人，完全不是。  
>> 在你们给的入场股价上，对顶尖人才来说依然有吸引力吗？  
>> 到目前为止，没有人告诉我不是。  
>> 你会在“找完美匹配的人”和“找一个足够好的人”之间怎么权衡？  
>> 前面我拿 PM 开过玩笑，但其实产品人还是需要的。只是我觉得，他们必须是“完美匹配”的人。如果不是，那可能弊大于利。所以我在这里比以前更挑剔。

>> 假设我是一个计算机系学生，在 Stanford、Imperial、Cambridge、ETH 之类地方读书。你基于你现在知道的一切，会给我什么建议，帮我度过未来五年的职业生涯？  
>> 现在其实是做工程师最好的时代。你拥有非常强大的工具，可以完成极大量的工作；而且你加入一个复杂代码库的速度，也比以往任何时候都更快，因为你可以随时问 AI 这个代码库是怎么回事，还能让它帮你规划改动。  
所以第一点，我会说，你应该非常乐观。  
但接下来更现实的问题是：怎么拿到工作？  
因为“构建东西”从来没有这么容易过，所以真正稀缺的变成了：主动性、品味和质量。  
所以我会鼓励你，去真的造东西，展现你的主动性和品味，做高质量的东西，然后把它们分享出来。  
我们会收到大量求职 inbound，不管是从 careers 页面投来的，还是在社交媒体上联系我的。对我个人来说，如果有人给我写信，附上一些有意思的想法和一个有意思的项目链接，那比一份普通简历更能吸引我。

>> 快问快答前最后一个问题：Claude Code 有什么地方做得让你很佩服、并且你真的学到了？  
>> 有好几件。最重要的一件是，早在去年，他们就做了一个非常容易上手、零设置、能直接在 terminal 本地运行的工具。后来当我们更重投入 Codex CLI，并且给它配上 GPT-5 这样的强模型后，我们的增长直接爆发。  
所以“在用户所在的位置迎接用户”“给他们一个简单好用的东西”“让他们自己慢慢升级使用方式”——这大概是我们从他们那里学到的最大一件事。

>> 那他们犯过什么错误，是你们从中反向学到的？  
>> 我觉得他们有点过度押注自己最初的命令行工具成功。归根结底，那种 UI 还是不够友好，很难扩展到纯 builder 之外的人群，也很难真正支持“委托给 agent”，因为通过那样的界面做委托，你得是一个相当强的 terminal/Tmux power user。  
这也是为什么我们做了 app。而 app 的市场反馈让我特别坚定：虽然开始时这是个风险决策，但现在我越来越觉得我们做对了。Codex app 更直观、更简单、没那么吓人，而且它天然会把你引向“把手从键盘上拿开，去委托给 agent”的工作方式。

>> 你提到 Dropbox。Dropbox 出来的 alumni 非常惊人。你从 Dropbox 带到 OpenAI 的最大一条产品经验是什么？  
>> 我完全不用想，就是我前面说的那件事：如果你在给终端用户造工具，你就必须把这个工具看成一个“engagement system”。如果人们不想用你的工具，如果它不是完成某件事最自然、最轻松的方式，那他们就不会用。  
我就是从观察 Slack 崛起里学到这个的。  
所以现在我们做这些 agent 时，我一直在想：如果我们把 agent 纯粹做成 workflow automation，它就永远像拔牙一样难启动。你得去请 Accenture 之类的人进来，部署 FDEE，过程很痛苦。  
但如果你能做出一个“人们真心喜欢用”的系统，即使他们一开始只是拿它完成局部任务，随着时间推移，他们会越来越会用它，系统也会越来越接上他们真正需要的工具，自动化也就会一层层加进来。当然，这两种路径并不互斥。

>> 如果今天你来做 Dropbox 的增长复兴，你会怎么做？  
>> 至少在我当年在 Dropbox 时，我们真正擅长的是桌面软件。而桌面软件现在简直又重新变得重要了。  
因为如果你是为生产力和知识工作优化，虽然你确实需要连接各种 system of record，但归根结底，一切还是发生在用户电脑上——要么在浏览器里，要么在本地应用里。  
所以我觉得，未来最先出现的生产力 agent 增益，会先发生在“直接在用户电脑上工作”的场景里：直接利用他们当下可用的东西，而不用先部署 FDEE。  
如果我是 Dropbox，我会想：我们在桌面软件和“叠在电脑之上的协作层”上有独特经验，怎么把这个优势转化成生产力 agent？这个方向虽然有点宽泛，但我会从这里切入。

>> 最后一个正式问题：我是在一个“利润率很重要”的世界里长大的。软件的高毛利一直是它成为好投资品类的重要原因。但现在很多推理密集型玩家的利润结构非常不同。你觉得我应该先把毛利放在一边，相信 token 成本会下降、关键是使用量和用户爱不爱；还是说毛利仍然非常重要？  
>> 我觉得两件事都对。成本肯定会大幅下降。与此同时，如果今年真的是 agent 在工作场景里大规模部署的一年，那它们也会开始连上各种系统，而这种连接会非常 sticky。  
所以我把今年看作一场竞赛。既然是竞赛，你就要先赢。那在过程中牺牲一些利润率，我觉得是可以接受的。

>> 好，快问快答。你在过去 12 个月里改变最大的一件看法是什么？  
>> 我加入 OpenAI 时——虽然那已经超过 12 个月了——我原以为，我们很快就会进入这样一个世界：大家都在和电脑共享屏幕，我们只需要对一个 agent 说话就行。结果完全错了。  
多模态模型的进展，比我预期得慢。所谓多模态，就是处理视频和音频的模型。真正发生的情况是：通过“代码”来操作电脑的 agent，才是正确路径。所以我对“如何把 AI 的好处带给所有人”的理解，发生了根本变化。至少短期内，主要不是通过视频和音频，而是通过会用电脑的 agent。

>> 你最尊重的“低调竞争对手”是谁？为什么？  
>> 我第一反应是 AMP。Sourcegraph 那帮人做的。他们的产品口碑非常好，总是能打出远超体量的效果。另一个我特别尊重他们的地方，是他们推动了整个 agent 标准化的一步，比如 agents.md、agents/skills 这些，让用户更容易管理他们正在尝试的不同 agent。我们当然也推出了 agents.md，但他们也有 agent.md，而 Quinn 甚至发推说：如果你们买下 `agents.md` 这个域名，我们就按你们的拼写来标准化。看起来是很小的一件事，但却开启了我认为非常棒的一整轮社区标准化。

>> 你觉得 OpenAI 对 Anthropic 广告的回应是正确的吗？  
>> 有很多不同的回应，但我听到的那个，我觉得是对的。那种回应大概是：一家公司的叙事很悲观，而另一家公司，也就是我们 OpenAI，更积极，告诉人们可以去构建、可以去梦想。我觉得那种回应很棒。  
>> 但 Sam 还写了篇文章。  
>> 你觉得那是个好回应吗？  
>> 我觉得是。我很喜欢 OpenAI 的一点是，大家都很 unapologetically 做自己，也都非常真实。所以那种回应对我来说是一个非常真实的回应，而我喜欢我们这样做。

>> 你在 Codex 期间做过的最难产品决策是什么？  
>> 我可以告诉你最痛苦的产品决策。  
有段时间 Codex Cloud 基本等于无限量使用。不是免费，你还是得订阅 ChatGPT，但用量不设限。我们其实一直知道，放得越久，未来往回收就越难。但那时候我们太专注于在其他更具 PMF 的维度上竞争，所以把这个决定不断往后拖。  
后来我们把无限量改成了更合理的限制后，用户反弹很大。其实真正强烈反对的只是很小一部分用户，他们会觉得一切都应该永远几乎免费。但社交媒体的讨论不会区分这些。所以那次让我学到一个痛苦的教训：你不能把“无限量”维持太久。

>> 这就像定价 grandfathering，定价真的太难了。你觉得五年后我们回头看，现在在工程或产品上正在做的什么事，会让我们说“天啊，当年我们居然这么干”？  
>> 第一件肯定是：手写代码。  
另一件更 spicy 的，可能是：手动管理部署和监控系统。  
我觉得大公司会很慢才采用，但很多创业公司可能会开始在一种全新的栈上构建——一个完全由 AI 管理的栈。不是说这个栈今天已经存在了，但未来会有：你给 agent 很强的确定性护栏，允许它回滚部署、做控制。  
于是，创办公司这件事会变成：先拿一个 agent，让它开始造东西；然后再接入更多 agent；最后甚至把你的联合创始人都加进这个 agent 工作系统里。也许你们的主要沟通工具，最后就是那个 agent 协作工具；CI 和部署流程不再由人痛苦地手工维护，而是 agent 在做。

>> 我还有个怪问题：agent 的护栏到底是谁来提供？是你们这些 agent provider 自己，还是会有第三方说“这个不能进 HR、那个不能进市场部”？  
>> 我觉得两种都会有。我们自己当然在护栏上投入很多。比如对于 coding agent，我们几乎是唯一真正在乎 OS 级 sandbox 的公司，Windows 上甚至原本没有这套东西，是我们在做，而且还开源，希望别人也能用。  
我们也在 connector 上投入很多，比如你可以让 agent 访问 Google Docs，我们会很认真地设计它在 Google Docs 上能做什么、不能做什么。  
但我也觉得，只靠我们做的这些最终不会完全够。未来一定还会有第三方提供非常定制化的护栏能力，满足不同公司的特殊需求。所以最后大概会是混合形态。

>> 最后一个问题。往前看十年，你最期待什么？  
>> 也许根本不用十年，可能会更快发生。  
我加入公司的一个私人使命是：我觉得即便是一年半前的模型，已经存在巨大的“能力剩余”——它们明明可以帮很多人，但我们还没做出正确的产品形态。所以像我这样的人得到的好处，远比我奶奶这样的人多。  
我最期待的就是：我们找到一种 AI 的最终形态，让它真的能帮助所有人，不管他们是不是在科技行业，尤其是那些不在科技行业的人，尤其是年纪更大的人。  
一个很具体的画面是：未来某一天，我们把一个 agent 加进家庭 WhatsApp 群，它就开始自然地对整个家庭有帮助，而没有人需要额外学习怎么用它。也许还有很多别的实现方式，但这是我脑海里最直观的一个画面。

>> 兄弟，我太感谢你了。谢谢你忍受我这些东一榔头西一棒子的提问和我这种跳跃式的大脑。你太棒了。  
>> 谢谢你。我也很感谢你包容我那些同样跳跃的回答。挺好的。
